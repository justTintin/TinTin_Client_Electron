## 三、待对齐问题清单（按优先级）

### Q1（P0·需裁决）match_id 下线后，服务端合成链路的关键词命中与客户端是两套判定

**现状**：客户端不再下发 `text_template_match_id`。服务端 concat 收到 `text_template_match_enabled + text_template_match_ids`（仅模板池）+ `subtitle_srt` 后，**退回旧口径自行命中**：常用关键词 ∪ 内置卖点词，不足由服务端 LLM 从字幕行补足（`text_template_match_llm` 默认开）。

**影响（三点）**：
1. **预览 ≠ 成片**：第四步效果预览轨与剪映草稿用的是客户端命中（产品关联词 + 客户端 LLM 兜底），服务端成片烧的是服务端自行命中——词、位置、数量都可能不同；
2. **产品关联词在服务端链路失效**：concat 契约没有词表字段（`text_template_words` 2026-09-11 已删），服务端不知道所选产品的关联词；
3. **确定性丧失**：原 match_id 机制（服务端存 events 7 天、concat 直接复用）保证预览=成片且同请求可复现；现在服务端 LLM 每次命中结果可能不同。

**候选方案（待裁决）**：
- **A（推荐）**：恢复下发词表——`text_template_words` / `fancy_words` 字段**仍在 concat 契约中**（2026-09-11 客户端停发，服务端字段未删；历史格式 `JSON.stringify(words)`），客户端把产品关联词（或 LLM 兜底提词结果）随请求下发。见下方「方案 A 接口支持度核查」；
- **B**：服务端在 concat 内按产品身份（brand/model 随请求下发或查会话）自行读产品资料关联词命中——客户端零改动，但要求服务端能取到「当前会话选中的产品」；
- **C**：维持现状，接受预览与成片不一致（不推荐）。

**方案 A 接口支持度核查（2026-09-19，基于 2026-09-18 live openapi 契约快照）**：

| 层级 | 字段 | 契约状态 | 结论 |
|---|---|---|---|
| 词表 | `text_template_words: string` | ✅ 在（default 空；09-11 前格式=`JSON.stringify(["词1",…])`） | **半支持**：字段在，但 ①09-11 后服务端读取逻辑是否保留未知；②与 `text_template_match_llm`（LLM 补足）的组合语义未定义——传词表时服务端是「只用词表」还是「词表∪常用词∪LLM」，决定成片是否忠实词源 |
| 花字词表 | `fancy_words: string` | ✅ 在 | 同上 |
| 事件清单 | （无 `text_template_events` 类字段） | ❌ 无 | 需服务端新增字段+烧制逻辑，才能做到客户端算好的命中事件逐帧复用（原 match_id+服务端存 events 机制即此用途，正随 match 一起删除） |

**客户端待办（A 落地时）**：`buildServerFxFields`（montage-final-ipc.js）恢复 `text_template_words`/`fancy_words` 下发，词源=`sharedProductInfo.keywords`（产品关联词）∪ LLM 兜底提词结果；约 10 行改动。**服务端待确认**：读取逻辑健在性 + 词表优先级语义 + 格式（JSON 数组串）。

### Q2（P0·待信息）产品资料关联关键词的字段名

契约中 `GET /api/product-library/search` 响应 schema=`unknown`（服务端从未声明 response model），字段名无从对源。客户端已做防御解析：`keywords` / `product_keywords` / `关键词`，接受 `string[]` 或顿号/逗号/分号/换行分隔字符串（`opsProductLibraryLogic.parseProductKeywords`，单测钉住）。**请服务端确认实际字段名与格式**；若是其它名字，客户端一行对齐。建议服务端为该端点补 response model，契约即可自证。

### Q3（P1·存量）`/text_templates/render-preview` 500

2026-09-10 已登记（服务端内部错误，动画预览接口不可用）；当前渲染层已不依赖（词条=纯关键词标记，2026-09-15 裁决），仅主进程命中行素材下载消费。待服务端修复或从契约删除。

### Q4（P1·随 contract:gen 收敛）14 条 API_PATHS 声明无契约对应业务域

`/health/capabilities`、`/health/check`、`/stats/workbench`、`/script/adjust-copywriting`、`/script/list` 等 14 条：客户端声明了路径常量但旧版 openapi 无对应业务域——要么契约太旧（服务端已新增），要么常量超前（端点不存在）。contract:gen 后逐条销项。另有 444 条契约路径客户端未用（预期，不处理）。

### Q5（P2）`/montage/concat` 契约清理

服务端删除 match 后，建议同步从 openapi 删除 `text_template_match_id` 字段及其描述（"textfx_clips 按序轮换标注 template_id / events 保存 7 天 / match_id 复用"等标注全部作废），避免契约自相矛盾。
