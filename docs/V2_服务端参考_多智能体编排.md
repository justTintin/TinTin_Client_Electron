## 十三、多智能体编排（服务端智能体化）

> 服务端接口需求单：[多智能体编排服务端接口需求.md](多智能体编排服务端接口需求.md)（S1~S6，当前状态见需求单实现状态）

> **决策（2026-08-08）**：工作台「一句话需求」要真正"拆解任务→分配给不同智能体→统一管理任务"，需要两层前提：
> ① **能力注册表**（编排器必须知道服务端/客户端/外部各有多少智能体、各自输入输出）；
> ② **编排器本身是一个元智能体（Orchestrator Agent）**，由 LLM 驱动规划/路由/监督。
> **方向：服务端先行「智能体化」**——先由服务端提供能力注册表与编排执行能力，客户端编排器骨架随后对接。

### 13.1 目标

- 一句话需求 → 智能体拆解 → 分配给不同子智能体 → 统一任务管理（进度/暂停/取消/重试/人工确认）。
- 服务端成为"智能体工厂"：能力可注册、可编排、可被多端共享调度。

### 13.2 现状盘点：智能体/能力分层（客户端视角，权威以服务端 /guide 为准）

| 层 | 能力单元（示例） | 同步/异步 |
|---|---|---|
| 服务端接口 | `/llm/chat/completions`、`/voxcpm/tts`、`/whisper/transcribe`、`/material/search|list|scan|serve|thumbnail|distinct|stock_search|web_download`、`/material/ocr`、`/material/score_clip`、`/montage/split|concat|beat|effect|auto`、`/vsr/remove`、`/digital-human/*`、`/api/storyboard/scripts`、`/prompt/image|video`、`/agent/*`、`/agent/chat`、`/scheduled/tasks`、`/tasks/unified/{id}`、`/editor/*`、`/review/*`、`/evaluate/*`、`/comfyui/*`、`/health` | 同步 + 异步两类 |
| 客户端本地工具 | ffmpeg（切/拼/混音/转码）、剪映草稿导出、封面（ffmpeg+rembg+Dreamina）、直播切片 | 同步/本地任务 |
| 外部工作流 | 数字人（RunningHub/ComfyUI）、即梦（本地 CLI） | 异步/第三方 |

> 说明：**"智能体"≠ 仅服务端接口**。编排器必须把三层统一注册成一张能力目录。

### 13.3 能力注册表（Agent Registry）

每个能力单元的结构（schema）：

```json
{
  "id": "tts_voice_clone",
  "name": "声音克隆/TTS",
  "tags": ["audio"],
  "description": "输入文案+参考音频，返回克隆语音",
  "executor": "server",            // server | client_tool | external
  "api": "POST /voxcpm/tts",
  "method": "POST",
  "path": "/voxcpm/tts",
  "input_schema": {"text": "string", "prompt_audio": "base64?", "speaker": "string?"},
  "output": {"audio": "file_ref"},
  "sync": true,                     // 同步返回 or 提交后轮询
  "needs_user_input": false,        // 是否需要人工确认/选素材
  "dependencies": [],
  "poll": "GET /tasks/unified/{task_id}"  // 仅异步能力
}
```

- 权威来源：服务端 `/guide` 提供接口级能力；客户端补充本地工具 + 外部工作流，两边合并成一张注册表。
- 客户端启动拉取服务端注册表，本地 JSON 兜底（离线可用）。

### 13.4 编排器 = 元智能体（Orchestrator Agent）

由 LLM 驱动五个阶段：

```
用户一句话 → Orchestrator Agent：
  1. Plan    拆解为步骤 DAG（能力A → 能力B → 能力C，含依赖/参数）
  2. Route   按能力注册表匹配并分配给对应子智能体
  3. Execute 同步调用 / 提交异步任务
  4. Monitor 轮询 /tasks/unified、失败重试、状态聚合
  5. Confirm 遇需人工确认节点（选素材/确认文案/试听）暂停，等用户确认后继续
```

### 13.5 驱动策略与演进

| 阶段 | 执行地 | 说明 |
|---|---|---|
| Step 1（客户端先行） | 客户端 Orchestrator 调服务端单能力接口 | 快速验证；plan 用可序列化 JSON |
| Step 2（plan 标准化） | 同一份 plan 由服务端执行引擎读取 | 客户端执行器换成"提交 plan + 轮询" |
| Step 3（服务端终态） | 服务端 Agent 编排 | 客户端只做：提交/轮询/人工确认/展示 |

> **plan 是纯 JSON（步骤/参数/依赖/中间产物引用）**，Step 1 写的拆解逻辑在 Step 3 不重写，只换执行地。
>
> **当前状态（2026-08-12）**：Step 3 已具备——`POST /agent/tasks mode=execute` 可执行 plan，`/agent/chat mode=plan` 负责自然语言拆解；客户端已完成注册表拉取、任务列表/确认/暂停/恢复/重试等骨架对接。

### 13.7 MCP 集成（能力调用协议与归属）

> **参考（2026-08-08）**：开源项目 [MediaHub](https://github.com/StartAI-Best/MediaHub) 的价值点——把素材库能力暴露成 **MCP Server**，AI 智能体（Claude/Cursor 等）通过标准 MCP 工具直接调用。对本项目的意义：**MCP 可作为「服务端智能体化」的子能力调用协议**，`list_tools` 天然就是能力注册表（正好回答"服务端有多少智能体"）。
>
> **实现（2026-08-12）**：服务端已提供 `server/mcp/server.py`（stdio JSON-RPC），`tools/list` 对齐注册表，`tools/call` 转调现有接口。

#### 归属结论

| 层 | MCP Server | 职责 | 优先级 |
|---|---|---|---|
| **服务端（主）** | 包装全部服务端能力为 MCP 工具 | TTS / 成片 / 素材检索 / 去字幕 / 混剪 / OCR / ComfyUI / LLM，供编排器与外部 AI 工具统一调用 | P0 |
| **客户端（可选）** | 包装本地轻工具为 MCP 工具 | 剪映导出 / ffmpeg / 封面 / 即梦 CLI，仅本机编排用 | P1~P2 |

- **重能力编排由服务端做**（符合「重活上服务端」+ 服务端智能体化方向）；客户端只暴露自己的本地轻工具，非必须、可后置。
- MCP **不替代** 13.6 的服务端编排接口（plan / 子任务树 / 人工确认仍由服务端负责），而是作为「子能力调用协议」标准化。

#### 落地

1. 服务端 MCP Server（已实现 `server/mcp/server.py`）：`list_tools` 返回能力清单（对齐 13.3 注册表 schema）；`call_tool` 转调现有接口。
2. 能力注册表 S1（13.6）与 MCP `list_tools` 的 tool 描述格式对齐，单一事实源。
3. 客户端 Orchestrator Agent 通过 MCP 调用子能力；外部 AI 工具（Claude/Cursor）同样可用，生态复用。

| S1 | 服务端编排执行（S2/S4/S5/S6） | S0 | 服务端可执行一份 plan，多端共享、断点续跑 |

# 多智能体编排服务端接口需求

> 来源：PRD_V2.2.md 第十三章（多智能体编排/服务端智能体化）
> 目的：服务端先行「智能体化」——能力可注册、可编排、可多端共享调度。
> 实现状态（2026-08-12 /guide 核对）：S1~S6 已全部在服务端上线，客户端已按 `studio/utils/agent_client.py` 对接；本文件保留需求单供追溯。

## 需求总览

| # | 接口 | 方法 | 优先级 | 状态 |
|---|------|------|--------|------|
| S1 | `/agent/registry` | GET | P0 | 已实现（36 server 能力） |
| S2 | `/agent/tasks` | POST | P1 | 已实现（mode=execute 执行 plan） |
| S3 | 子任务模型（`/tasks/unified` 扩展） | - | P0 | 已实现（`a_*` 任务返回子任务树） |
| S4 | `/agent/tasks/{id}/confirm` | POST | P1 | 已实现（waiting_user_input → queued） |
| S5 | 中间产物登记 | POST | P1 | 已实现（自动扫描 + POST /agent/artifacts） |
| S6 | 编排任务管理（列表/暂停/取消/重试） | GET/POST | P1 | 已实现（pause/resume/retry/cancel） |

## S1 能力注册表（P0）

- `GET /agent/registry`：返回全部可编排能力清单。
- 能力字段（schema）：

```json
{
  "id": "tts_voice_clone",
  "name": "声音克隆/TTS",
  "tags": ["audio"],
  "description": "输入文案+参考音频，返回克隆语音",
  "executor": "server",            // server | client_tool | external
  "api": "POST /voxcpm/tts",
  "method": "POST",
  "path": "/voxcpm/tts",
  "input_schema": {"text": "string", "prompt_audio": "base64?", "speaker": "string?"},
  "output": {"audio": "file_ref"},
  "sync": true,
  "needs_user_input": false,
  "dependencies": [],
  "poll": "GET /tasks/unified/{task_id}"  // 仅异步能力
}
```

- 期望覆盖：LLM、TTS、ASR、素材检索/分析、视频处理（split/concat/beat/vsr）、成片任务、ComfyUI 等（以 /guide 为准）。

## S2 提交编排任务（P1）

- `POST /agent/tasks`：登记/提交编排任务；`mode=execute` 提交 plan 由服务端 Orchestrator 自动执行。
- plan 为可序列化 JSON：`{goal, steps: [{id, capability, params, depends_on, needs_user_input}], ...}`；
  能力必须是注册表 `executor=server` 能力，成环/悬空依赖提交即 400。
- 返回 `{id: "a_xxx", status: "running", execution: "started"}`，进入 `/tasks/unified/{id}` 轮询。
- 自然语言拆解改走 `POST /agent/chat`，`mode=plan` 返回 `task_id` 后再轮询。
- 不带 `mode` 可手动登记：`{goal, capability, params, parent_task_id}`。

## S3 子任务模型（P0）

- 任务增加 `parent_task_id`，支持父子任务树；任务 id 前缀 `a_`。
- `GET /agent/tasks/{id}` 返回 `{task, children: [...]}` 嵌套树；`/tasks/unified/{id}` 已打通，`a_*` 前缀返回完整子任务树。
- 状态取值：`queued | running | waiting_user_input | completed | failed | paused | cancelled`。
- 父任务 `derived_status` 由子任务推导：全 completed→completed；任一 failed→failed；任一 waiting_user_input→waiting_user_input；
  任一 running→running；任一 queued→queued；否则 paused/cancelled；`children_progress` 为子任务均值。

## S4 人工确认节点（P1）

- step 带 `needs_user_input=true` 时，该子任务执行前置为 `waiting_user_input` 暂停（如选素材、确认文案、试听音频）。
- 客户端展示中间结果后 `POST /agent/tasks/{子任务id}/confirm` → `queued`，执行器继续推进。

## S5 中间产物登记（P1）

- 步骤完成后执行器自动扫描响应中的文件引用登记到 `agent_artifacts`；也可手动 `POST /agent/artifacts`：
  `{task_id, kind(audio|video|image|text|json|other), file_ref, meta?}`。
- `GET /agent/tasks/{id}/artifacts` 返回自动 + 手动产物；下游用 `${step_id.artifact}` 引用首个产物 file_ref。

## S6 编排任务管理（P1）

- 列表：`GET /agent/tasks?root_only=false&status=...&parent_task_id=...`（默认只列根任务）。
- 暂停/恢复/重试/取消：`POST /agent/tasks/{id}/pause|resume|retry|cancel`。
- 断点续跑：任务状态持久化；`retry` 仅 failed/cancelled，failed/cancelled 子任务重置为 queued，completed 子任务保留复用；
  服务重启自动恢复 running 根任务。

## 验收

- S1：客户端能拉到统一能力清单，展示"服务端当前有多少可编排智能体"（实测 36 server 能力）。
- S2/S3：服务端可执行一份 plan，多端共享、断点续跑、失败重试。
- S4/S5：支持"跑一半等用户确认"与下游引用中间产物。
- S6：客户端编排任务管理可列表/暂停/恢复/重试/取消，断点后自动续跑。
