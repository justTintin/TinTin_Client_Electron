## 一、希区柯克镜头 & 特效镜头

### 1.1 目标

智能混剪增加电影级运镜效果，提升视频质感和专业度。

### 1.2 特效镜头类型

| 类型 | 效果 | 适用场景 |
|------|------|---------|
| 希区柯克变焦 (Dolly Zoom) | 主体不变，背景拉近/拉远 | 悬念、强调、转场 |
| 推拉镜头 (Push/Pull) | 画面徐徐推进或拉远 | 开场、产品展示 |
| 摇晃镜头 (Shake) | 画面震动 | 冲击感、动作场景 |
| 慢动作 (Slow Motion) | 逐帧插值降速 | 细节展示、情绪渲染 |
| 快速缩放 (Speed Ramp) | 变速 + 缩放组合 | 卡点、节奏变化 |
| 旋转过渡 (Spin) | 画面旋转切入 | 快节奏转场 |
| 镜像/翻转 (Flip) | 水平/垂直翻转过渡 | 对比、创意转场 |

### 1.3 技术方案

```
ffmpeg 滤镜链：
  zoompan  →  推拉/希区柯克
  minterpolate  →  慢动作
  rotate + zoompan  →  旋转缩放
  setpts/atempo  →  变速
```

### 1.4 智能匹配

根据画面内容自动推荐特效：
- 产品特写 → 慢动作 + 推近
- 人物出场 → 希区柯克
- 快节奏 BGM → 快速缩放
- 文字/字幕出现 → 弹入动画

## 二、剪映 (PR) 驱动 & 审美判断

### 2.1 目标

将 AI 生成的粗剪 XML/JSON 导出，驱动剪映进行精细化剪辑。剪辑时做审美判断。

### 2.2 导出格式

- 剪映支持通过 DRT (Draft) 文件导入工程
- 已有 `utils/jianying_exporter.py` 基础，需扩展
- 导出内容：时间轴、转场、滤镜、字幕、音频

### 2.3 审美判断模块

| 维度 | 判断标准 | 技术 |
|------|---------|------|
| 构图 | 三分法、主体居中比例 | `_score_clip()` 已有的主体突出分 |
| 色彩 | 色调统一性、饱和度 | cv2 色彩直方图分析 |
| 节奏 | BPM 与镜头切换卡点 | ffmpeg 提取 BPM，镜头时长对齐 |
| 连贯性 | 相邻镜头的色彩/亮度跳变 | 帧间差异检测 |
| 安全区 | 字幕/标题是否在安全区内 | OCR + 位置分析 |

### 2.4 剪映驱动流程

```
混剪粗剪 → 导出 DRT JSON
  → 剪映打开工程
  → AI 逐镜头审阅：
      构图建议、色彩调整建议、转场建议
  → 用户确认/修改
  → 导出成品
```

### 2.5 接口（以服务端 /guide 文档为准）

| 能力 | 描述 |
|-----|------|
| 导出剪映工程 | 将粗剪时间轴导出为剪映 DRT 文件 |
| 审美评价 | LLM 审美评价（构图/色彩/节奏） |
| 节奏分析 | BPM 卡点对齐分析 |

### 3.6 导入 PR / 剪映模板

**目标**：支持导入 Premiere Pro (PR) 和剪映的工程文件作为模板，AI 自动解析结构并适配到素材库。

#### 支持格式

| 来源 | 文件格式 | 解析内容 |
|------|---------|---------|
| 剪映 (CapCut) | `.drt` (Draft JSON) | 时间轴、片段长度、转场、滤镜、文本、音频轨道 |
| Premiere Pro | `.xml` (FCP XML) | 序列结构、剪辑片段、转场、标记 |
| After Effects | `.aep` → `.xml` | 合成结构（间接） |
| 自定义 JSON | `.tpl.json` | 本系统原生格式 |

#### 导入流程

```
用户上传 PR .xml / 剪映 .drt
  → 服务端解析工程结构：
      提取 片段时长、转场类型、BGM、文本模板、层级
  → 转换为内部模板 JSON（3.2 格式）
      每段标注 tag（自动识别或手动标注）
  → 模板存入模板库（可分享、售卖）
  → 使用时自动匹配素材库素材
```

#### 技术方案

**剪映 DRT 解析**（已有 `utils/jianying_exporter.py` 基础，扩展读取方向）：
- DRT 文件本质是 JSON，包含 `tracks`、`segments`、`transitions`
- 提取轨道结构 → 映射到内部模板 slot
- 提取转场类型 → 映射到 ffmpeg xfade 参数
- 提取文本模板 → 作为 overlay 模板

**Premiere Pro XML 解析**：
- FCP XML 标准格式，包含 `<sequence>`、`<clip>`、`<transition>`
- 解析 clip 时长、顺序
- 提取 transition 类型 → 映射

#### 模板分享

| 功能 | 说明 |
|------|------|
| 导出模板 | 内部模板 JSON 可导出为 `.tpl.json` |
| 导入模板 | 支持 `.tpl.json` / `.drt` / `.xml` |
| 模板市场 | 服务端模板库，用户可上传/下载 |
| 模板版本 | 模板可升级，兼容旧版素材 |

### 3.7 接口（以服务端 /guide 文档为准）

| 能力 | 描述 |
|-----|------|
| 导入模板 | 上传 PR/剪映 工程文件，解析为模板 |
| 导出模板 | 导出模板为 .tpl.json |
| 上传模板市场 | 上传模板到模板市场 |
| 模板市场列表 | 查询可用模板 |

### 3.8 产品成片页模板交互

`compile_video_page.py` 的“产品成片” tab 按模板流程重新组织：

```
左侧产品区
  → 选择产品（必须）
  → 原“性能参数 / 核心卖点”区域改为“模板库”
  → 点击“卖点文案”按钮可弹窗/浮层展示原核心参数与卖点（供参考）
  → 选择模板后，右侧“模板参数”区域按模板 params 动态生成表单
  → 点击“设置默认”把参数全部恢复为模板默认值
  → 点击“开始执行”提交一键成片任务
```

右侧参数区标题由“可选设置”改为“模板参数”，包含：
- 通用字段：素材目录、配音音频、TTS 音色、片头（MG 开场）、封面、字幕文案、比例、每段时长、成片数量、总时长等。
- 模板自定义字段：根据所选模板的 `params` 定义动态生成（字符串/整数/颜色/JSON 等）。
- “设置默认”按钮：将当前模板的所有参数重置为 `defaults` 或 `params` 中的默认值。

模板选择规则：
- 通过服务端 `/mg/templates` 拉取模板列表（包含内置模板 + 自定义模板）。
- 当从“素材检索”跳转过来且已携带相关素材时，保留现有素材，不强制覆盖；仅按模板填充文案/参数缺省项。
- 未选择模板时沿用原逻辑（不依赖模板）。

提交一键成片任务：
- 在 `compile_video_page._collect_params()` 中增加 `template_id` 和 `template_params` 字段。
- `template_id` 为所选模板 id（内置模板直接使用 `id`，自定义模板使用 `backend`）。
- `template_params` 为当前界面收集到的模板自定义参数值。
- 服务端 `video_montage` 任务按需读取模板参数，用于生成开场/转场/片尾/字幕样式等。

### 3.9 脚本成片全链路闭环（下一步）

> **状态（2026-08-10）**：🟡 主链路已通，提交后无进度/结果闭环。本节为脚本成片下一阶段的**具体实现规划**。

#### 3.9.1 现状（已实现部分）

- 脚本来源：服务端 `GET /api/storyboard/scripts` 列表 + `GET /api/storyboard/scripts/{id}` 详情；服务端不可达时回退本地 `KNOWLEDGE_MEDIA_DIR/<选题>/storyboard/*.json` 扫描（`compile_video_page._populate_scripts`）；
- 提交：`POST /scheduled/tasks`，`task_type=storyboard_montage`，参数契约（实测 id=12/15）：`params = {shots:[{index,shot_type,duration,visual,audio,material_path,material_type,sfx}], voice_settings:{speaker}, count, ratio, ...}`（文案字段为 `audio`，服务端自动搜素材 → TTS → FFmpeg → 质量评分）；
- 提交后仅提示「任务已提交（ID=xxx），请到成片任务页查看」，脚本成片 tab 本身**无进度、无结果**。

#### 3.9.2 缺口与具体实现

**① TTS 音色选择（客户端，先行）**
- 现状：`voice_settings.speaker` 写死 `"default"`（`_collect_script_params`）；
- 实现：脚本 tab 设置行新增「音色」下拉，复用 `_populate_voices()`（`load_voice_samples()` 本地样本）+ 默认项；
- 依赖：本地音色样本文件服务端不可见，需与音色注册方式对齐——若服务端支持上传参考音频，则提交时随任务上传样本；若服务端已有 speaker 库，则下拉改拉服务端列表（以 `/guide` 为准，缺失则按第七章惯例走 `POST /interfaces/request` 提需求）。

**② 提交后页内进度跟踪（客户端）**
- 现状：提交完就断链，用户必须切「成片任务」页；
- 实现：`_submit_script` 拿到 `task_id` 后在本 tab 启动轮询 Worker（3s 间隔，复用 `scheduled_task_client.get_task` → `GET /tasks/unified/{id}`，失败回退 `/scheduled/tasks/{id}`），脚本状态区展示阶段化进度条：`素材匹配 → TTS 配音 → 视频合成 → 质量评分 → 完成/失败`（阶段名以服务端 status/progress 字段实际返回映射，未知状态原样展示）；
- 完成/失败后停止轮询，按钮恢复可用；页面切走不中断（Worker 挂 `track_worker`）。

**③ 结果页内播放/下载（客户端）**
- 实现：任务完成后从结果取成片 URL（服务端文件走 `/material/serve` 流式），复用 `VideoPreviewDialog` 挂在本 tab 结果区：▶ 播放 + ⬇ 下载到输出目录；
- 勾选「成片后评价预测」时，结果卡片旁同时展示服务端质量评分字段（有则显示，无则隐藏，不阻塞）。

**④ 每镜头素材可见与干预（服务端配合，二期）**
- 现状：服务端自动搜素材，客户端看不到匹配了什么；分镜页已引用的素材（`material_path/material_id`）虽随 shots 提交但服务端不收；
- 实现（需服务端扩展契约）：a) 任务结果返回每镜头实际使用的素材 id/URL → 客户端预览表增加「实际素材」列并可点击预览；b) 服务端 `storyboard_montage` 支持 shots 指定 `material_id` 时优先于自动匹配 → 分镜页已引用素材直接生效；
- 契约缺失时按第七章惯例提交 `/interfaces/request`，落地前本项挂起。

**⑤ 多变体择优可见（服务端配合，二期）**
- 现状：`count` 个变体由服务端进化机制选最优 1 个输出；
- 实现（需服务端扩展结果结构）：返回全部变体 + 各自评分 → 客户端结果区横向列出，任选播放/下载，默认选中最高分。

#### 3.9.3 实施拆分与验收

| 阶段 | 内容 | 依赖 | 预估 | 验收标准 |
|------|------|------|------|----------|
| 一期（纯客户端） | ①音色选择 + ②页内进度 + ③结果播放/下载 | 现有 `/scheduled/tasks`、`/tasks/unified/{id}` | 1 周 | 提交后不离开本页即可看到阶段进度，完成后直接播放/下载成片；音色随任务生效 |
| 二期（服务端配合） | ④镜头素材可视化/干预 + ⑤多变体择优 | 服务端结果结构扩展（先走接口需求流程） | 1~2 周 | 预览表可见每镜头实际素材并可替换；变体可选 |

> 涉及的服务端字段（任务阶段枚举、成片 URL、每镜头素材、变体列表与评分）一律以 `/guide` 实测为准；实现前先用真实任务 id 核对 `/tasks/unified/{id}` 返回结构，字段缺失走 `POST /interfaces/request` 提需求（同第七章流程）。

```
客户端选择模板 / 新建自定义模板
```

- `mg_quote`：quote + author 金句引用。
- `mg_benchmark`：title/specs{cpu,gpu,ram,ssd}/bars[] 性能对比柱状图。

## 五、垂类剪辑模板

### 5.1 电影解说

**模板结构**：
```
片头 (3s) → 开场悬念 (5s) → 剧情概述 (15s) 
→ 名场面 1 (10s) → 分析点评 (8s) → 名场面 2 (10s) 
→ 总结升华 (5s) → 片尾引导关注 (3s)
```

**AI 能力**：
- 自动识别电影名场面（高潮+转折）
- LLM 生成解说文案（悬念钩子 + 剧情 + 点评）
- TTS 配音（解说风格声音样本）
- 画面匹配解说文案时间轴

### 5.2 知识科普

**模板结构**：
```
问题引入 (5s) → 概念解释 (10s) → 案例演示 (10s) 
→ 数据支撑 (5s) → 实用技巧 (8s) → 总结 + 引导 (5s)
```

**AI 能力**：
- LLM 根据选题生成科普脚本
- 素材库中匹配知识类画面（产品/图表/示意图）
- 自动生成字幕 + 标注
- 字幕高亮关键词

### 5.3 通用模板引擎 + 导入

所有垂类模板统一用 JSON 描述结构，引擎可扩展。**支持从剪映/PR 导入模板**（参见 3.6 导入流程）：

```json
{
  "category": "movie_review",
  "name": "电影解说-3min",
  "duration": 180,
  "source": "built-in",       // built-in | imported | market
  "source_file": "",           // 原始导入文件名
  "segments": [...],
  "voice_profile": "解说_男声",
  "bgm_profile": "悬疑_紧张"
}
```

**模板来源**：

### 7.2 现状与问题

- **现状**：分镜脚本保存在客户端本地 `KNOWLEDGE_MEDIA_DIR/<选题>/storyboard/*.json`，保存时默认只导出 Excel，需手动选择 JSON 才会生成供脚本成片使用的文件（已临时用"保存时自动生成 JSON"缓解）。

  1. 「一键成片 → 脚本成片」只扫描本地 `.json`，默认流程下看不到已保存脚本；
  2. 脚本不跨机器、不跨用户共享，无法统一备份；

- **管理**：服务端脚本支持更新与删除（分镜页可管理已保存脚本）；
- **兼容**：本地 JSON 保留为离线缓存 / 兼容来源，服务端不可达时回退本地扫描。

## 十、封面制作模板化

> **设计理念（2026-08-02 对齐）**：封面制作使用**封面类模板（type=cover）**，与动效模板（type=motion）严格区分——
> 封面是「静态画面 + 参数驱动」，动效是「视频动效模板」。上传的模板**先进入图层编辑模式拆成图层处理**
> （支持 PSD 逐层解析），也可拆分为封面模板参数（标题/副标题/卖点/背景色/文字色/比例）驱动本地渲染。

### 10.1 目标

将封面制作页改造为「封面模板（type=cover）驱动」的流程，同时保留本地图层式编辑器作为高级微调入口。

### 10.2 当前状态（2026-08-02）

- 页面拆分为「图层编辑」+「封面模板」两个 tab：
  - **图层编辑**：本地 `QGraphicsScene` + `QPainter` 分层渲染（背景/主体/标题/副标题/卖点…），高级微调入口。
  - **封面模板**：模板库只展示**封面类模板**（统一模板接口 `GET /templates?type=cover`，兜底内置 cover 模板），
    右侧按模板 `params` 生成「封面参数」表单（标题/副标题/卖点/背景色/文字色/比例）；
    点「预览」把参数**拆到图层编辑器**并本地渲染 PNG，点「导出」输出 PNG。
- **上传模板（图片/PSD）**：上传后**先进入图层编辑模式**，把文件拆分为图层处理：
  - PSD：用 `psd_tools` 逐层解析，每个可见图层成为图片图层，并生成扁平预览图；
  - 普通图片：整图作为底层「模板参考」图层，可配合「模板→复刻构图」AI 自动排版。
- 已移除「上传视频」入口（封面制作不依赖视频素材）。

### 10.3 流程

```
上传模板（图片/PSD）→ 进入图层编辑（拆图层处理 / AI 复刻构图）
                                │
封面模板 tab：选封面模板(type=cover) → 填封面参数
                                │
          预览 = 参数拆到图层 → 本地 QPainter 渲染 PNG
                                │
          导出封面 PNG（写入素材库）
```

模板参数（type=cover）：
- 封面比例：9:16 / 16:9 / 1:1。
- 标题、副标题、卖点文案（支持多行）。
- 背景色、文字颜色。
- （可扩展）主体图片、字体、字号、位置、装饰元素、Logo、安全区提示。

### 10.4 接口

| 能力 | 接口 | 说明 |
|-----|------|------|
| 封面模板列表 | `GET /templates?type=cover` | 统一模板接口按封面类型过滤（服务端暂未提供 cover 模板，客户端用内置 cover 模板兜底） |
| 封面模板校验/保存 | `POST /templates/validate` / `POST /templates` | 统一模板接口（type=cover） |
| 预览/导出 | 本地 QPainter 渲染 | 参数拆到图层编辑器渲染 PNG；服务端提供 type=cover 渲染后，可改用 `POST /templates/render` + `GET /templates/render/result|download/{task_id}` |
| PSD 图层解析 | psd_tools（客户端内嵌） | 上传 PSD → 逐层拆分为图片图层 |

- 高级参数（模板、配音音色、字幕样式、转场等）默认取合理值，放「更多设置」折叠区
- 从现有页面包装，不新造底层能力

#### 12.3.3 结果中心

- 统一展示所有任务进度（复用成片任务/任务队列页）
- 完成态动作：预览 → 下载 → 发布（待评估）→ 送入剪辑精修（→ 智能混剪 / 剪映草稿）

### 12.4 剪辑模式设计

- 完整保留现有侧边栏全部专业入口，默认首页换成专业工作台
- 增强方向（演进）：时间线可视化、多轨、关键帧、逐镜头精修、PR/剪映导出（剪映导出已支持多片段+转场）
- 运营↔剪辑衔接：运营成片一键「送入智能混剪 / 剪映草稿精修」

### 12.5 技术选型与实现方案（2026-08-17 更新）

**决策：双模式 = 两个进程，分阶段渐进，不整体重写。**

**运营模式 = 独立 Electron 应用（工作台 + 素材浏览器一体）；剪辑模式 = 原 PySide6。**
切换由薄壳切换器主导（当前阶段 PySide6 承载，设计为可移交，见 12.5.2）。

#### 12.5.1 进程架构

```
PySide6 主进程（常驻：登录/授权/托盘/配置；剪辑模式全部专业页面）
   |  顶部"运营/剪辑"切换按钮
   ├─ 剪辑模式：自身全屏显示（现状）
   └─ 运营模式：spawn Electron（工作台 + 素材浏览一体，独立窗口）
        |        → PySide6 自身 hide()（或最小化到托盘）
        └─ Electron 内"返回剪辑" → 通知 PySide6 显示 → 自己退出
数据共享：同一份 studio/data + ai_config.json + 素材库/产出目录（素材浏览器已能读）
```

- **PySide6 是当前阶段的常驻父进程与切换主导者**：有单例/托盘/授权，Electron 由它 spawn（asset_browser_client 已有拉起能力）。
- **Electron 是运营模式窗口**：关窗即退，被拉起/退出由 PySide6 管理（PySide6 关 = 先杀 Electron 子进程）。
- **切换只是视图变化**：数据完全共享，零迁移。

#### 12.5.2 可移交的切换器（防止未来锁死）

切换器只做"读配置 / 写配置 / 拉起对方 / 收退出信号"，不掺业务逻辑，主导权未来可移交：

1. **角色配置放共享文件** studio/data/mode_config.json（存当前角色），不存 PySide6 内存——未来 Electron 或独立启动器可直接读；
2. **双方都有切换按钮（对称）**：PySide6 顶部"运营模式"、Electron 内"返回剪辑"；未来 PySide6 退场时，Electron 已具备独立切换能力；
3. **切换器做薄**：几十行（读配置→spawn 对方→收退出信号），业务零耦合；
4. **主导权移交路径**：PySide6 →（运营模式稳定）→ Electron 内自持切换 →（剪辑逐步 Web 化）→ 独立薄启动器读配置拉起对应 exe。迁移成本 = 重写薄模块，非重写客户端。

#### 12.5.3 阶段划分

| 阶段 | 内容 | 技术栈 | 涉及模块 | 预估 |
|------|------|--------|---------|------|
| **P0** | 切换器（薄壳 + mode_config.json）+ 运营模式 Electron 壳（工作台 Tab：对话/智能体列表/模型选择，纯服务端 HTTP）+ 素材浏览并入同窗口多 Tab | Electron（apps/asset-browser 扩展）+ 新增工作台 Web 页 | asset-browser/main.js、renderer 新增 workbench 页、asset_browser_client.py、gui_main.py（切换按钮） | 1-2 周 |
| **P1** | 工作台补全：任务卡片 / 极简向导 / 结果中心 / 一键成片与声音克隆向导；本地能力（技能管理器、文件选择）经 IPC 或本地 Python 服务桥接 | Electron + 复用服务端接口（/voxcpm/tts、/scheduled/tasks、/montage/concat、/material/search、/llm/chat/completions） | renderer 新增向导页、main.js IPC 扩展 | 1-2 周 |
| **P2** | 自然语言智能体编排（LLM 意图识别→组装参数→调接口链）+ 一键发布；剪辑模式逐步 Web 化试点 | 客户端 LLM 编排 + 现有 worker 链 | 新增 agent_orchestrator、发布对接 | 1-2 周 |

- 运营模式先做**纯服务端交互**（对话/智能体/模型/素材），不依赖本地，Web 化无障碍；
- PySide6 不是"作为 Electron 页面"，而是**保留为剪辑模式进程**；Electron 里的工作台是**新建的 Web 页面**（对话/卡片逻辑用 JS 重写，服务端契约与数据格式复用）。


### 12.6 演进路线与依赖

| 里程碑 | 内容 | 依赖 | 验收 |

### 12.7 服务端依赖结论

- 任务卡片覆盖范围受限处（如分镜脚本存储、模板市场等 PRD 标注「待服务端实现」的能力）在 P0/P1 暂不做或先做本地版。

## 十三、多智能体编排（服务端智能体化）

> 服务端接口需求单：[多智能体编排服务端接口需求.md](多智能体编排服务端接口需求.md)（S1~S6，2026-08-12 已实现）

> **决策（2026-08-08）**：工作台「一句话需求」要真正"拆解任务→分配给不同智能体→统一管理任务"，需要两层前提：
> ① **能力注册表**（编排器必须知道服务端/客户端/外部各有多少智能体、各自输入输出）；
> ② **编排器本身是一个元智能体（Orchestrator Agent）**，由 LLM 驱动规划/路由/监督。
> **方向：服务端先行「智能体化」**——先由服务端提供能力注册表与编排执行能力，客户端编排器骨架随后对接。

### 13.1 目标

- 一句话需求 → 智能体拆解 → 分配给不同子智能体 → 统一任务管理（进度/暂停/取消/重试/人工确认）。
- 服务端成为"智能体工厂"：能力可注册、可编排、可被多端共享调度。

### 13.2 现状盘点：智能体/能力分层（客户端视角，权威以服务端 /guide 为准）

| 层 | 能力单元（示例） | 同步/异步 |
|---|---|---|
| 服务端接口 | `/llm/chat/completions`、`/voxcpm/tts`、`/whisper/transcribe`、`/material/search|list|scan|serve|thumbnail|distinct|stock_search|web_download`、`/material/ocr`、`/material/score_clip`、`/montage/split|concat|beat|effect|auto`、`/vsr/remove`、`/digital-human/*`、`/api/storyboard/scripts`、`/prompt/image|video`、`/agent/*`、`/agent/chat`、`/scheduled/tasks`、`/tasks/unified/{id}`、`/editor/*`、`/review/*`、`/evaluate/*`、`/comfyui/*`、`/health` | 同步 + 异步两类 |
| 客户端本地工具 | ffmpeg（切/拼/混音/转码）、剪映草稿导出、封面（ffmpeg+rembg+Dreamina）、直播切片 | 同步/本地任务 |
| 外部工作流 | 数字人（RunningHub/ComfyUI）、即梦（本地 CLI） | 异步/第三方 |

> 说明：**"智能体"≠ 仅服务端接口**。编排器必须把三层统一注册成一张能力目录。

### 13.3 能力注册表（Agent Registry）

每个能力单元的结构（schema）：

```json
{
  "id": "tts_voice_clone",
  "name": "声音克隆/TTS",
  "tags": ["audio"],
  "description": "输入文案+参考音频，返回克隆语音",
  "executor": "server",            // server | client_tool | external
  "api": "POST /voxcpm/tts",
  "method": "POST",
  "path": "/voxcpm/tts",
  "input_schema": {"text": "string", "prompt_audio": "base64?", "speaker": "string?"},
  "output": {"audio": "file_ref"},
  "sync": true,                     // 同步返回 or 提交后轮询
  "needs_user_input": false,        // 是否需要人工确认/选素材
  "dependencies": [],
  "poll": "GET /tasks/unified/{task_id}"  // 仅异步能力
}
```

- 权威来源：服务端 `/guide` 提供接口级能力；客户端补充本地工具 + 外部工作流，两边合并成一张注册表。
- 客户端启动拉取服务端注册表，本地 JSON 兜底（离线可用）。

### 13.4 编排器 = 元智能体（Orchestrator Agent）

由 LLM 驱动五个阶段：

```
用户一句话 → Orchestrator Agent：
  1. Plan    拆解为步骤 DAG（能力A → 能力B → 能力C，含依赖/参数）
  2. Route   按能力注册表匹配并分配给对应子智能体
  3. Execute 同步调用 / 提交异步任务
  4. Monitor 轮询 /tasks/unified、失败重试、状态聚合
  5. Confirm 遇需人工确认节点（选素材/确认文案/试听）暂停，等用户确认后继续
```

### 13.5 驱动策略与演进

| 阶段 | 执行地 | 说明 |
|---|---|---|
| Step 1（客户端先行） | 客户端 Orchestrator 调服务端单能力接口 | 快速验证；plan 用可序列化 JSON |
| Step 2（plan 标准化） | 同一份 plan 由服务端执行引擎读取 | 客户端执行器换成"提交 plan + 轮询" |
| Step 3（服务端终态） | 服务端 Agent 编排 | 客户端只做：提交/轮询/人工确认/展示 |

> **plan 是纯 JSON（步骤/参数/依赖/中间产物引用）**，Step 1 写的拆解逻辑在 Step 3 不重写，只换执行地。
>
> **当前状态（2026-08-12）**：Step 3 已具备——`POST /agent/tasks mode=execute` 可执行 plan，`/agent/chat mode=plan` 负责自然语言拆解；客户端已完成注册表拉取、任务列表/确认/暂停/恢复/重试等骨架对接。

### 13.6 服务端智能体化接口（2026-08-12 /guide 核对：已实现）

| # | 接口 | 说明 | 状态 |
|---|---|---|---|
| S1 | `GET /agent/registry` | 能力注册表：返回全部可编排能力（schema 见 13.3） | 已实现（36 server 能力） |
| S2 | `POST /agent/tasks` | `mode=execute` 提交 plan 自动执行；自然语言拆解走 `/agent/chat mode=plan` | 已实现 |
| S3 | 子任务模型 | 父任务 + 子任务树（`parent_task_id`），`/tasks/unified` 返回 `a_*` 树状状态 | 已实现 |
| S4 | 人工确认节点 | 子任务状态 `waiting_user_input`；`POST /agent/tasks/{子任务id}/confirm` 继续 | 已实现 |
| S5 | 中间产物登记 | 自动扫描 + 手动 `POST /agent/artifacts`；`GET /agent/tasks/{id}/artifacts` 查询 | 已实现 |
| S6 | 编排任务管理 | 列表/暂停/恢复/重试/取消；支持断点续跑（不依赖客户端在线） | 已实现 |

### 13.7 MCP 集成（能力调用协议与归属）

> **参考（2026-08-08）**：开源项目 [MediaHub](https://github.com/StartAI-Best/MediaHub) 的价值点——把素材库能力暴露成 **MCP Server**，AI 智能体（Claude/Cursor 等）通过标准 MCP 工具直接调用。对本项目的意义：**MCP 可作为「服务端智能体化」的子能力调用协议**，`list_tools` 天然就是能力注册表（正好回答"服务端有多少智能体"）。
>
> **实现（2026-08-12）**：服务端已提供 `server/mcp/server.py`（stdio JSON-RPC），`tools/list` 对齐注册表，`tools/call` 转调现有接口。

#### 归属结论

| 层 | MCP Server | 职责 | 优先级 |
|---|---|---|---|
| **服务端（主）** | 包装全部服务端能力为 MCP 工具 | TTS / 成片 / 素材检索 / 去字幕 / 混剪 / OCR / ComfyUI / LLM，供编排器与外部 AI 工具统一调用 | P0 |
| **客户端（可选）** | 包装本地轻工具为 MCP 工具 | 剪映导出 / ffmpeg / 封面 / 即梦 CLI，仅本机编排用 | P1~P2 |

- **重能力编排由服务端做**（符合「重活上服务端」+ 服务端智能体化方向）；客户端只暴露自己的本地轻工具，非必须、可后置。
- MCP **不替代** 13.6 的服务端编排接口（plan / 子任务树 / 人工确认仍由服务端负责），而是作为「子能力调用协议」标准化。

#### 落地

1. 服务端 MCP Server（已实现 `server/mcp/server.py`）：`list_tools` 返回能力清单（对齐 13.3 注册表 schema）；`call_tool` 转调现有接口。
2. 能力注册表 S1（13.6）与 MCP `list_tools` 的 tool 描述格式对齐，单一事实源。
3. 客户端 Orchestrator Agent 通过 MCP 调用子能力；外部 AI 工具（Claude/Cursor）同样可用，生态复用。
### 13.8 优先级与验收

| 里程碑 | 内容 | 依赖 | 验收 |
|---|---|---|---|
| S0 | 服务端能力注册表（S1）+ 子任务模型（S3） | /guide 扩展 | 客户端能拉到统一能力清单并展示"服务端有多少智能体" |
| S1 | 服务端编排执行（S2/S4/S5/S6） | S0 | 服务端可执行一份 plan，多端共享、断点续跑 |
| C1（客户端） | Orchestrator Agent 骨架 + 注册表合并 + plan 生成 | S0 可用或本地兜底 | 一句话"数字人口播带货视频"→ 自动拆解并逐个执行/轮询 |
| C2（客户端） | 编排任务管理页（进度/暂停/取消/人工确认） | S1 | 与工作台结果中心统一 |

> 状态（2026-08-12 /guide 核对）：✅ S0/S1 已实现——`/agent/registry`（36 server 能力）、`mode=execute` plan 执行、子任务树、人工确认、产物登记、暂停/恢复/重试/取消均已在服务端上线；客户端骨架已对接（`agent_client.py`、编排任务管理页）。

### 14.4 自动上架业务流程

```
导入数据包（目录 / ZIP）
  → 校验：sku.xlsx、主图/详情页/sku图目录非空、文件名店铺关键词匹配
  → 检查 / 启动 Chrome 调试模式（默认 127.0.0.1:9222，固定 user-data-dir）
  → 复用已登录抖店会话；未登录则提示扫码
  → 校验当前页面店铺与目标店铺一致
  → 进入商品创建页
  → 阶段1：主图 / 标题 / 自动选类目 / 下一步
  → 阶段2：基础信息 / 图文信息 / 价格库存 / 服务与履约 / 其他信息
  → 保存草稿强校验（轮询“必填报错 / 保存成功 / URL 跳转”）
  → 按配置保存草稿或直接上架
  → 结果、截图、日志写入 data/auto_listing/
```

### 14.5 关键业务规则

- 一个批次 = 一个商品：`sku.xlsx` 中所有行属于同一商品的多规格（SKU），只允许填入当前商品页的「价格与库存」表格，严禁拆分为多个商品发布。
- 数据包命名必须包含店铺关键词（如“桔柚”或“555”），与所选店铺不匹配时终止并提示修改命名。
- 通过 URL 特征区分阶段：无参数 `create` 为阶段1，`create?` 进入详情配置页；按当前活跃 Tab 支持断点续跑。
- 保存成功判定必须经过页面状态轮询，避免“看起来点了保存、实际失败”的虚假完成。
- 自动上架任务使用客户端 Worker 直接执行，不依赖外部 PowerShell/CMD 终端。

## 十五、客户端 ASR/OCR 流程优化（待办）

> 状态（2026-08-17）：记录为**后续优化项**，当前实现可用，暂不实施。

### 15.1 现状（已实现）

- **OCR**：识别已全部走服务端 `POST /material/ocr`，客户端本地仅做图像裁剪、视频抽帧、结果写盘，无本地识别模型。
- **ASR**：识别走服务端 `POST /whisper/transcribe`，客户端本地仅做"ffmpeg 提取音频"预处理后上传。

### 15.2 ASR 待优化点

**当前流程**（每个需要语音识别的功能重复执行）：
```
视频 → 本地 ffmpeg 转 16k 单声道 wav → 上传服务端 /whisper/transcribe → 服务端识别 → 返回 segments
```

涉及功能（8 处调用 `transcribe_remote`）：
- 视频转文字（`transcription_page.py`）
- 智能混剪·转文字（`video_montage_page.py`）
- 语音克隆（`voice_clone_page.py`）
- 声音样本库（`voice_samples_page.py`）
- 知识库媒体转写（`my_knowledge_page.py`）
- 直播切片（`live_clip_page.py`）
- 扩展桥接采集字幕（`extension_bridge.py`）
- 视频索引流水线（`video_indexer.py`）

**优化方向（待评估）**：
1. **音频提取下沉服务端**：客户端直接上传视频，服务端负责 ffmpeg 解封装提取音频 + Whisper 识别，客户端不再依赖本地 ffmpeg；需评估上传体积/耗时。
2. **音频提取结果缓存**：同一视频重复转写（如克隆+索引+剪辑）时，复用已提取的音频或已识别的 segments，避免重复 ffmpeg 转换与重复上传。
3. **统一转写入口**：8 处调用收敛为单一服务（客户端统一 API 或服务端任务化），减少重复代码与维护成本。
4. **前置校验**：上传前服务端校验音轨存在性/时长，避免无效请求。

### 15.3 优化价值

- 减少客户端本地依赖（ffmpeg 环境要求）；
- 避免同一素材跨功能重复提取音频/重复识别；
- 统一 ASR 调用链，降低维护成本。

### 15.4 验收标准（实施时）

- 视频转文字 / 语音克隆 / 知识库等全部 ASR 场景走统一入口，行为与现状一致；
- 重复转写同一视频可命中缓存，不再重复上传识别；
- 客户端无需本地 ffmpeg 即可完成 ASR（音频提取在服务端或已缓存）。

## 十六、整体目标：逐步减少客户端本地对 Python 的依赖（架构原则）

> 状态（2026-08-17）：**全局架构方向**，贯穿后续所有迭代。客户端保持"薄客户端"定位：
> GUI/交互/本地文件处理留在客户端，**AI 能力与可复用逻辑逐步向服务端收敛**。

### 16.1 原则

1. **AI 能力服务端化**：识别（OCR/ASR）、推理（LLM/视觉）、编排（智能体/能力注册）一律在服务端，客户端不做本地推理。
2. **本地 Python 依赖最小化**：客户端只保留"无法避免的本地处理"（GUI、文件读写、媒体预处理、与本地硬件的交互），可下沉的逻辑逐步迁移。
3. **能力是能力，不是智能体**：客户端只负责展示与交互，能力归属服务端统一管理（与已有架构约定一致）。

### 16.2 当前本地 Python 依赖盘点（2026-08-17）

| 依赖点 | 位置 | 现状 | 归属 |
|---|---|---|---|
| GUI 框架 | 整个 `studio/`（PySide6） | 客户端本体，保留 | 客户端 |
| OCR 识别 | `ocr_client.py` → 服务端 | 已服务端化 ✓ | 服务端 |
| ASR 识别 | `asr_client.py` → 服务端 | 已服务端化 ✓（本地仅 ffmpeg 提音频） | 服务端 |
| 镜头分割 | `/montage/split` | 已服务端化 ✓（scenedetect 本地兜底已删） | 服务端 |
| 技能执行 | `data/skills/*`、`skill_manager.py` | 本地技能可执行 Python 脚本 | **待评估** |
| 定时任务 | `local_scheduler.py`（schtasks + python.exe） | 本地 Windows 计划任务跑 Python | **待评估** |
| 环境检测/终端 | `env_config_page.py`、`terminal_page.py` | 本地 Python 子进程 | 保留（系统运维属性） |
| ffmpeg 处理 | `video_compiler.py`、`montage/workers/*` | 本地子进程 ffmpeg（剪辑/拼接/配音/混音） | **待评估**（与服务端合成并存） |
| 浏览器采集桥接 | `extension_bridge.py` | 本地服务 + 部分远程调用 | 保留（本地硬件交互） |

### 16.3 迁移路线（按优先级）

| 优先级 | 项 | 方向 | 前置条件 |
|---|---|---|---|
| P1 | ASR 音频提取下沉/缓存 | 服务端解封装或复用已提取音频；统一 8 处转写入口 | 服务端支持直接收视频或音频缓存（见 15.2） |
| P1 | 技能执行服务端化 | 本地技能脚本迁服务端（executor=server）；客户端技能仅保留"引导式"（如视频下载） | 服务端技能运行时就绪 |
| P2 | 定时任务服务端化 | Windows schtasks + 本地 python → 服务端任务队列 | 服务端定时任务接口（已有 /scheduled/*）扩展 |
| P2 | ffmpeg 合成收敛 | 剪辑拼接/配音/混音统一走服务端合成，本地 ffmpeg 仅作预览/临时处理 | 服务端 montage 合成链路稳定（USE_SERVER_CONCAT 已开启） |

### 16.4 不迁移的边界（保留本地）

- **GUI 与交互**：PySide6 客户端本体；
- **本地文件/素材管理**：下载走客户端素材浏览器（用户既定原则）、本地读写；
- **系统运维**：环境检测、终端、桥接服务（本地硬件/浏览器交互）；
- **实时预览**：本地 ffmpeg 预览、抽帧等低延迟操作。

### 16.5 验收标准（逐步达成）

- 每迁移一项：客户端对应功能不再依赖本地 Python 子进程/本地模型；
- 客户端发布包可逐步精简（python_embeded 依赖项减少）；
- 服务端成为能力唯一入口，客户端保持薄壳；
- 迁移过程不回归现有功能（迁移项有等价验收）。


### 16.6 行业参照与客户端技术选型（2026-08-17 实测本机安装）

> 依据：本机已安装 WorkBuddy 与 TraeWork（TRAE SOLO），以下结论来自**实际检查安装目录代码构成**，非网络传闻。

**竞品客户端技术栈（实测）**：

| 软件 | 客户端框架 | 本地运行时 | AI 能力位置 |
|---|---|---|---|
| TraeWork（TRAE SOLO） | Electron（VSCode 内核 fork，`product.json` 标注 `vscodeVersion: 1.107.1`） | Node.js（内置） | 云端（`icube-normal.trae.ai`、WebSocket `frontier`） |
| WorkBuddy | Electron（`app.asar` 269MB，含 webview 内嵌腾讯文档） | Node.js（内置） | 云端 |

**共同规律**：两者均为"**Web UI（Electron）+ 本地 Node.js I/O + AI 全云端**"的薄客户端架构——客户端只做界面渲染、本地文件/系统/浏览器控制，AI 推理与编排 100% 在服务端。这与本 PRD 第十六章"减少客户端本地对 Python 的依赖"方向一致。

**客户端技术选型分析（不重写为 Electron）**：

- **PySide6 是产品骨架，不是壳**：本工程代码实测 `QTableWidget` 194 处（素材/分镜/任务表格）、`QMediaPlayer` 73 处（视频预览）、`QThread` 47 处（后台 worker）、`QWebEngineView` 3 处。核心交互深度依赖 Qt，重写 Electron 等于推倒重来，成本数月且无收益。
- **Web 技术已按需引入**：素材下载浏览器（`apps/asset-browser`）已是独立 Electron 应用（`main.js` + preload + renderer，内嵌 node/ffmpeg/yt-dlp），与主程序通过 `handoff.json` 松耦合。适合 Web 的场景已经用 Electron。
- **问题不在 UI 技术，而在本地承载了不该承载的能力**：当前待优化项（技能执行、定时任务、ffmpeg 合成）与 UI 框架无关，换 Electron 一样要服务端化。重写不解决 16.2 盘点的任何问题。

**结论**：
1. 不因竞品用 Electron 而重写客户端，PySide6 继续作为桌面壳；
2. 坚持并推进 16.3 迁移路线（技能/定时任务/ffmpeg 合成服务端化）；
3. 未来可继续"Web 化适合的页面"（如管理型页面做服务端渲染），进一步缩薄本地 shell，而非推翻重写。
