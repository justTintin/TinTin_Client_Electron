# 文案混剪「一镜多片·按时长装填」技术实现方案

> 2026-09-21 立项。用户裁决背景：智能匹配（方案 C）上线后，绑定量级仍是「一镜一片、全长使用、不裁不加速」——
> 镜标 8 秒、素材只有 3 秒（或反之）时成片节奏错配。本文是升级为「一镜可绑多片、按时长装填」的完整技术方案。
> 依据分级（铁律 9）：用户裁决 > 服务端契约实测 > 代码事实 > 工程习惯。文中事实均引代码/实测出处。

## 一、问题定义

### 1.1 现状（2026-09-21 智能匹配 v1 上线后）

| 环节 | 现状 | 出处 |
|---|---|---|
| 绑定结构 | `tab.clipIdxs: number[]`——每镜恰 1 个分割镜头序号；`shot.material_path` 单值 | CopyStep2Panel.vue / useCopyMontageStep3Voice.ts |
| 装填 | 无。一镜一片，不管镜标时长几秒 | 同上 |
| 成片镜长 | = 素材全长。预合成=纯拼接：不洗牌、不裁时长、不重排 | useCopyMontageStep2Concat.ts L209 |
| 智能匹配 | LLM 按语义选主片（候选经景别桶>时长窗 0.4–2.5×>评分预筛）+ 循环轮转兜底 | copyMontageAssignLogic.ts |
| 转场 | `/montage/concat` 的 `transition` 是**全局参数**：所有相邻片段之间一律应用（实测 transition_duration 固定 0.5） | 提交载荷实测 2026-09-21 22:24:58 main.log |
| 旁白耦合 | 批量配音每行 target_duration=该镜视频时长（2026-09-19 提交 915080d）→ **成片镜长直接决定该段旁白时长** → 镜长错配会传导到口播节奏 | voice-tts 契约实测 |

### 1.2 两类错配

- **欠长**（素材总长 < 镜标）：镜被「注水」——旁白 8 秒的叙述压在 3 秒画面上，或被迫复用素材。
- **超长**（单片 > 镜标）：镜被「拖堂」——3 秒的动作镜头用了 12 秒素材全长，成片节奏拖沓。

### 1.3 目标口径（升级后）

1. 一镜可绑**多片**，按时长装填：按顺序取片累计，达到镜标时长即封镜（每镜至少 1 片）。
2. 单片超过镜标剩余空间时的处置：**裁剪或加速**（待裁决，见 §八）。
3. 成片镜长 ≈ 镜标时长（允许容差），使 AI 分镜的节奏设计成立、旁白段时长与叙事语义对齐。

## 三、方案总览：两阶段

### 阶段一（推荐首发）：客户端镜内预渲染，concat 契约零变更

```
智能匹配 v2（LLM 选主片）
   → 贪心装填（欠长补片）                    ← 纯本地、纯逻辑层
   → 超长处置（本地 ffmpeg 裁剪 or setpts 加速）← 纯本地，复用 F5 先例
   → 镜内多片预拼接为「每镜一个中间文件」        ← 纯本地（硬切拼接，镜内不加转场）
   → 每镜一个文件整组 files 上传 → /montage/concat（镜间转场照旧，契约零变更）
```

- **镜=上传单元**：`clip_shot_types`/`edge_speedup` 语义不变（按镜文件摊平，F2 口径兼容）；
  全局 `transition` 恰好只落在**镜与镜之间**——「镜内硬切、镜间转场」的表达难题被本地预拼接自然消解。
- **代价**：每镜一次本地 ffmpeg 中转编码（N 镜串行，预估每镜 1080p superfast 1–3s 量级，实测后补数据）+
  中间文件上传（增量流量）。质量损耗一代（superfast 中转）。
- **回退**：镜内仅 1 片且未裁剪未加速时，该镜直接用原 `serverPath` 走旧路径？——**不可混用**（F3：files 与
  clip_urls 互斥、整组切换）。口径：方案内任一镜触发了预处理，整组走 files；全部未触发则维持纯 clip_urls。

### 阶段二（优化项，报服务端排期）：逐片段规格契约

提案字段（multipart 新增 `clip_specs` JSON 数组，`clip_urls` 保序对齐）：

```json
[{"url": "…/clip_003.mp4", "start": 0.0, "duration": 3.0, "speed": 1.0, "group": 0},
 {"url": "…/clip_007.mp4", "start": 1.2, "duration": 2.6, "speed": 1.0, "group": 0},
 {"url": "…/clip_011.mp4", "start": 0.0, "duration": 4.0, "speed": 1.0, "group": 1}]
```

- `start/duration`=裁剪点，`speed`=逐片变速，`group`=镜分组（转场只落在 group 边界）。
- 服务端直裁直变速：省本转编码与上传、无代际质量损失；`edge_speedup` 语义保持兼容。
- **动工前置**（铁律 6/9）：契约以服务端实测为准——先 probe `/openapi.json` 与测试环境联调通过再切换，
  客户端按响应能力探测做双轨（服务端支持 clip_specs 直发；不支持回退阶段一本地路径）。

## 五、分配与装填算法（智能匹配 v2，纯逻辑层 copyMontageAssignLogic.ts 扩展）

### 5.1 主片选择（不变）

LLM 语义选主片 + 循环轮转兜底，现状口径原样保留。差异仅在**时长预筛窗收紧**（可选裁决项）：
候选时长窗从 0.4–2.5× 收紧到 0.8–1.5×（超长大幅减少）；窗内空桶回退宽窗。

### 5.2 贪心装填（新，欠长处置）

```
装填(镜, 主片):
  picked = [主片]; covered = 主片.duration
  候选序 = 预筛排名（copyMontageAssignLogic prefilter 同口径，跳过已选 key——按 F 指纹去重）
  while covered < target × SEAL_RATIO(裁决，建议 0.9) 且 候选未尽:
      取下一候选 push；covered += 其全长
  return picked   // 每镜至少 1 片（主片兜底保证）；素材池耗尽 → 后续镜装 0 片走拦截提示
```

- 封镜后**末片可能超出**剩余空间：末片超长部分按 §5.3 处置（裁到剩余量 / 整片加速）。
- 素材复用：跨镜、跨脚本允许（与循环兜底同哲学），但**同一镜内**同 key 不重复。
- 改造自 F6 `assignScenesToShots`：顺序游标 → 按镜预筛序取片（语义对齐智能匹配）；纯函数可测。

### 5.3 超长处置（新，待裁决三选一）

| 选项 | 实现 | 优点 | 代价 |
|---|---|---|---|
| A 裁剪（推荐默认） | 本地 ffmpeg `-ss 0 -t remaining`（关键帧就近），镜长=镜标 | 节奏最准；实现最薄 | 硬切点可能戛然（转场可掩护） |
| B 加速 | 本地 `setpts=PTS/target`，倍率封顶 2.0（再超回退 A） | 动作完整 | 快放观感；倍率>1.5 明显 |
| C 换片 | 装填/匹配阶段优先选短候选（5.1 收紧窗） | 从源头减少超长 | 素材少时无片可换 |

**推荐组合 C+A**：匹配端收紧时长窗减少超长概率 → 残余超长一律裁剪。加速（B）作为每镜可覆写的
高级选项（后续 UI 加「该镜加速」开关），不进默认链路。

### 5.4 兜底链不变

LLM 失败 → 主片循环轮转兜底（v1 口径）→ 装填器照跑（兜底主片同样装填）。任何镜装 0 片 → 汇总明示
+ `tabsAllBound` 拦截合成（口径同 F8）。
